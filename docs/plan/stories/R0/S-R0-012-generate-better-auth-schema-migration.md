## 1. Why
Better Auth stores users, sessions, accounts and verification tokens in our database. Its tables must exist as a reviewed SQL migration before auth is mounted.

## 2. Context pack
- Relevant docs: `docs/plan/adr/ADR-0005-auth-provider.md`; `docs/plan/06_DATA_AND_AUTH.md` §2 (auth tables are generated, not hand-edited), §4.
- **Files to read first:** `apps/api/drizzle.config.ts`, `apps/api/src/infra/db/schema/index.ts`, `apps/api/test/helpers/db.ts`.
- **Files to create:** `apps/api/better-auth.cli.ts` (generator input only), `apps/api/src/infra/db/schema/auth.ts` (generated), `apps/api/migrations/0000_auth.sql` (generated by drizzle-kit), `apps/api/test/auth-schema.test.ts`.
- **Files to modify:** `apps/api/src/infra/db/schema/index.ts` (`export * from "./auth"`), `apps/api/package.json` (dependency `better-auth@^1.7.23`).
- **Files you must NOT touch:** `packages/**`, `legacy/**`.
- Env vars: none.

## 3. Design notes
- `better-auth.cli.ts` exists only so the generator can read the configuration. It is not imported by the Worker:

```ts
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
export const auth = betterAuth({
  database: drizzleAdapter({} as never, { provider: "sqlite" }),
  socialProviders: { google: { clientId: "x", clientSecret: "x" } },
});
```

- Generator command (verified name 2026-11-14): `pnpm dlx auth@latest generate --config ./better-auth.cli.ts --output ./src/infra/db/schema/auth.ts`.
- Expected tables and the columns the tests assert: `user` (`id`, `name`, `email` unique, `email_verified`, `image`, `created_at`, `updated_at`), `session` (`id`, `token` unique, `user_id`, `expires_at`, `ip_address`, `user_agent`), `account` (`id`, `account_id`, `provider_id`, `user_id`, token columns), `verification` (`id`, `identifier`, `value`, `expires_at`).
- After generation, run `pnpm --filter @slj/api db:generate -- --name auth` to produce the SQL migration from the Drizzle schema.
- Edge cases: column names may be camelCase in the generated file; keep whatever the generator emits (do not rename), but the tests below must pass against the actual names — adjust the test's column list to the generated names if they differ and say so in the PR.

## 4. Steps
1. Add `better-auth`; `pnpm install`.
2. Create `better-auth.cli.ts`; run the generator → `src/infra/db/schema/auth.ts` exists and exports four tables.
3. Export from `schema/index.ts`; run `db:generate` → `migrations/0000_auth.sql` contains four `CREATE TABLE` statements.
4. `pnpm --filter @slj/api db:migrate:local` → applies `0000_auth.sql`.
5. Write the test → `pnpm --filter @slj/api test` passes.
6. Commit: `feat(api): generate Better Auth schema migration (S-R0-012)`.

## 5. Acceptance criteria
- AC1: Given a fresh test database, when migrations are applied, then tables `user`, `session`, `account`, `verification` exist (`SELECT name FROM sqlite_master WHERE type='table'`).
- AC2: Given two users with the same email, when inserting the second, then the insert fails (unique constraint).
- AC3 (negative): Given a `session` row whose `user_id` does not exist, when inserting, then it fails (foreign key).
- AC4: Given a deleted user, when querying their sessions, then none remain (cascade).

## 6. Tests to write

## 9. Stop conditions
- The generator fails or needs a live database: stop and report. A Tier-3 executor or the founder then writes `auth.ts` by hand from https://www.better-auth.com/docs/concepts/database (core schema) — do not guess column names.
- The generated schema has no foreign key or no unique index on `session.token`: stop and report.
